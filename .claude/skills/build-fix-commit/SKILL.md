이 프로젝트(`D:\Unreal_Project\Capstone`)는 자동화된 테스트 하네스가 없는 Windows용 UE5.7 C++ 프로젝트입니다 (`CLAUDE.md` 참고). 따라서 "테스트"는 곧 **컴파일이 깨끗하게 통과하는지**를 의미하고, 그 이상의 논리적 검증은 에디터에서의 수동 플레이테스트(PIE)로만 가능합니다. 이 스킬은 그 현실에 맞춘 워크플로입니다: 코드 작성 → 빌드 → (버그 있으면) 즉시 수정 후 재빌드 → 깨끗하면 커밋.

## 언제 이 워크플로를 따르는가

`Source/Capstone/` 아래 C++ 파일을 새로 작성하거나 수정하는 모든 작업. 오타 수정 한 줄짜리처럼 명백히 컴파일에 영향이 없는 경우(주석/문서 수정 등)는 매번 전체 빌드를 돌릴 필요는 없지만, 그 외에는 기본적으로 이 루프를 거친 뒤에야 작업이 "끝났다"고 보고하세요.

## 1단계 — 코드 작성/수정

요청받은 C++ 변경을 수행합니다. 이 저장소의 기존 관례를 따르세요:
- 게임플레이 로직의 원본은 C++이고, 블루프린트는 보통 메시/애니메이션/위젯 연결 및 노출된 프로퍼티 조정용입니다. C++만 봐서는 기능이 빠진 것처럼 보이면 대응되는 블루프린트(`BP_*`)에 설정이 있을 수 있다는 점을 사용자에게 알려주세요 — `.uasset`은 바이너리라 직접 읽거나 고칠 수 없습니다.
- `GameInfo.h`는 사실상 이 프로젝트의 PCH에 가까운 공용 헤더입니다.
- 기존 헤더의 한글 주석 인코딩 문제(EUC-KR/CP949)는 무관한 작업 중에 건드리지 말고, 새로 쓰는 한글 주석은 UTF-8로 작성하세요.

## 2단계 — 빌드로 검증

이 프로젝트에는 유닛 테스트가 없으므로, "테스트"의 1차 관문은 컴파일입니다. 다음 명령으로 CapstoneEditor 타겟을 빌드하세요:

```
"C:\Program Files\Epic Games\UE_5.7\Engine\Build\BatchFiles\Build.bat" CapstoneEditor Win64 Development -project="D:\Unreal_Project\Capstone\Capstone.uproject"
```

주의점:
- UE 빌드는 수 분 걸릴 수 있으니 넉넉한 타임아웃을 주거나 백그라운드로 실행하고 완료를 기다리세요. 짧은 타임아웃으로 중간에 포기하고 "빌드 실패"로 오판하지 마세요.
- 에디터가 이미 켜져 있으면 실행 파일이 잠겨 있어 링크가 실패할 수 있습니다. 그런 실패가 나오면 "빌드 코드 오류"가 아니라 "에디터를 먼저 닫아야 한다"는 것을 사용자에게 알려주세요 — 코드를 억지로 고치려 하지 마세요.
- 성공 여부는 종료 코드와 출력 로그의 `Error` / `error(s)` 카운트로 판단하세요. `0 error(s)` 이더라도 새로 만진 파일과 관련된 경고가 있다면 진짜 버그의 신호일 수 있는지 살펴보세요 (예: 초기화 안 된 변수, 항상 참/거짓인 조건, 타입 축소 경고). 스타일성 경고(줄 길이 등)까지 쫓아다닐 필요는 없습니다 — 이번에 건드린 코드와 관련 있고 실제 동작에 영향을 줄 수 있는 것만 신경 쓰세요.

## 3단계 — 버그는 즉시 고치고 재빌드, 깨끗해질 때까지 반복

빌드 실패나 의심스러운 경고를 발견하면:
1. 에러 메시지가 가리키는 코드를 직접 확인하고 원인을 이해한 뒤 수정하세요 — 에러를 없애기 위해 억지로 타입을 캐스팅하거나 `#pragma`로 경고를 숨기는 식의 임시방편은 피하세요.
2. 다시 빌드하고, 새 에러가 없는지 확인하세요. 한 에러를 고치다 다른 에러가 생기는 경우가 흔하니, 완전히 깨끗해질 때까지 이 루프를 반복하세요.
3. 여러 번 시도해도 같은 지점에서 막히거나, 원인이 이번 작업 범위 밖(예: 엔진 설치 문제, 관련 없는 기존 코드의 구조적 문제)이라면 계속 억지로 파고들지 말고 사용자에게 상황을 설명하고 방향을 물어보세요.

## 4단계 — 컴파일 이후의 검증 한계를 인정하기

빌드가 깨끗해졌다고 해서 로직이 맞다는 보장은 없습니다. 이 저장소에는 자동 테스트가 없으므로, 컴파일러가 잡을 수 없는 게임플레이 로직 버그(예: 데미지 계산이 미묘하게 틀림, 퀘스트 진행도 갱신 안 됨)는 사람이 직접 PIE로 플레이해봐야 잡을 수 있습니다. 없는 테스트 하네스를 지어내거나 "테스트 통과"라고 과장하지 말고, 다음과 같이 정직하게 전달하세요:
- "컴파일은 깨끗합니다. [구체적으로 확인해볼 시나리오]를 에디터에서 플레이테스트해 보시겠어요?"
- 변경 내용이 순수 리팩터링이거나 명백히 안전한 범위라면 이 확인을 생략하고 바로 커밋 여부를 물어봐도 됩니다 — 매번 형식적으로 물을 필요는 없습니다. 판단이 애매하면 물어보는 쪽을 택하세요.

## 5단계 — 커밋 전에 무엇을 커밋할지 보여주기

빌드가 깨끗한 경우에만 커밋을 진행하세요. 빌드가 깨진 상태로는 절대 커밋하지 않습니다.

- `git status`로 전체 변경 사항을 확인하세요. 이번에 스킬이 직접 수정한 C++ 파일(`Source/Capstone/**/*.cpp`, `*.h`)만 스테이징 대상으로 삼으세요.
- `.uasset`, `.umap` 등 바이너리 콘텐츠 파일은 사용자가 에디터에서 직접 작업한 결과물일 수 있습니다. 이번 세션에서 스킬이 만든 변경이 아니라면 자동으로 스테이징하지 말고, "이런 파일들도 변경되어 있는데 같이 커밋할지" 사용자에게 물어보세요.
- 스테이징할 파일과 커밋 메시지 초안을 사용자에게 보여주고 확인을 받은 뒤 커밋하세요 (이 세션의 git 안전 수칙과 동일 — 커밋은 되돌리기 번거로운 공유 상태 변경이므로 매번 확인).
- 커밋 메시지는 이 저장소의 기존 스타일을 따르세요: 간결한 한국어 한 줄 요약, 무엇을 왜 바꿨는지 위주 (예: `git log` 참고 — "버그 해결 및 아이템 시스템 생성 완료", "퀘스트 시스템 경험치 시스템 완료" 같은 톤). 여러 줄로 나눌 필요는 보통 없습니다.
- hook을 건너뛰거나(`--no-verify`), 강제 푸시하거나, 기존 커밋을 amend하지 마세요. 새 커밋을 만드세요.

## 요약 체크리스트

1. C++ 작성/수정
2. Build.bat으로 CapstoneEditor 빌드
3. 에러/의심스러운 경고 → 원인 파악 후 수정 → 재빌드 (깨끗해질 때까지 반복)
4. 컴파일 이후 영역은 정직하게: 필요하면 플레이테스트 요청, 지어내지 않기
5. 커밋 대상(diff/파일 목록)과 메시지를 보여주고 확인받은 뒤 커밋 — 빌드 깨진 채로는 커밋 금지
